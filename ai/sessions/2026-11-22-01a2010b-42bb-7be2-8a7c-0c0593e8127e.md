Your **six endpoints cover the required product surface**. I would keep them and use synchronous requests for issuance and export.

Your six tables cover the business entities, but I recommend **two additional tables**:

- **`bulk_operations`** to remember idempotency keys and replay the original outcomes for A2–A3.
- **`audit_events`** to record issuance and revocation for A2 and A7.

The current [schema](/Users/xinyuyang/projects/OceanAI/backend/internal/store/bootstrap.sql) already includes `audit_events`. The main addition would be `bulk_operations`.

The smallest architecture is one Gin application, PostgreSQL transactions, and the React UI. Issuance can finish within its HTTP request; the UI shows “Issuing…” while waiting and then displays the returned outcomes.

**I would define the API contracts as follows:**

All six endpoints require the existing `X-Actor-Email` header. Middleware looks up the admin and derives `tenant_id`; clients never supply the authoritative tenant.

| Endpoint | Request | Response and behavior |
|---|---|---|
| `GET /api/courses` | No required parameters | Current tenant’s courses: `id`, `title`. |
| `GET /api/certificates` | `search`, `sort`, `direction`, `page`, `page_size` | A **page** of matching tenant certificates, plus `total`, `page`, and `page_size`. |
| `GET /api/certificates/:id` | Certificate ID | Certificate details, local issue date/time, status; `404` for missing or cross-tenant IDs. |
| `POST /api/courses/:id/issue` | Required `Idempotency-Key`; initially an empty JSON object | Process the course’s enrollments and return an operation ID, counts, and per-learner outcomes. Replays return the stored result; changed requests return `409`. |
| `POST /api/certificates/:id/revoke` | Certificate ID; initially no body | Return the revoked certificate. Repeating it returns the same state without another audit event. |
| `GET /api/certificates/export` | Same `search`, `sort`, `direction` as the list | Download all matching rows as CSV, ignoring list pagination. |

For example:

```http
GET /api/certificates?search=Alex&sort=issue_date&direction=desc&page=1&page_size=25
```

**The data model can stay compact:**

| Table | Essential fields | Important constraints |
|---|---|---|
| `tenants` | `id`, `name`, `timezone` | Valid IANA timezone, such as `Australia/Sydney`. |
| `admins` | `email`, `tenant_id` | Each admin belongs to one tenant. Existing email-based identity is sufficient. |
| `courses` | `id`, `tenant_id`, `title` | Titles need not be unique. |
| `learners` | `id`, `tenant_id`, `name` | Names need not be unique. |
| `enrollments` | `tenant_id`, `course_id`, `learner_id`, `completed_at` | Unique tenant/course/learner combination; null completion means incomplete. |
| `certificates` | `id`, `tenant_id`, `course_id`, `learner_id`, `serial_number`, `issued_at`, `status` | Unique serial; unique tenant/course/learner combination; status is `ACTIVE` or `REVOKED`. |
| `bulk_operations` | `id`, `tenant_id`, `actor_email`, `idempotency_key`, `request_hash`, `response_status`, `response_body`, `created_at` | Unique **tenant/admin/key** combination. Store the final response as JSONB. |
| `audit_events` | `id`, `tenant_id`, `certificate_id`, `actor_email`, `action`, `occurred_at` | Unique certificate/action combination for this limited lifecycle. |

Keep the existing composite foreign keys so an enrollment cannot connect an East course to a West learner. Apply the same tenant consistency to audit references.

Two deliberate scope decisions simplify this model:

- One enrollment represents one learner taking one course; repeated course attempts are outside this assessment.
- Revocation is terminal. Bulk issuance skips an enrollment that already has a certificate, including a revoked one. Reissuing would require an explicit additional lifecycle.

A separate operation-results table is unnecessary: `response_body` can hold the per-learner outcomes.

**The most important design is the issuance transaction—A2, A3, and A4 depend on it.**

1. Resolve the actor and confirm the course belongs to that tenant.
2. Begin a transaction.
3. Attempt to insert the operation record under its unique tenant/admin/key.
4. If the key already exists, compare the request fingerprint. Different fingerprint: `409`. Same fingerprint: return the stored response.
5. For a new operation, inspect enrollments in a consistent learner-ID order.
6. Insert eligible certificates with `ON CONFLICT ... DO NOTHING RETURNING ...`. Write an issuance audit only when a certificate was actually inserted.
7. Save the complete response and commit certificates, audits, and operation together.
8. Send success only after commit.

The fingerprint includes the HTTP action, course ID, and canonicalized request body. **Do not include course ID in the key’s uniqueness constraint**: otherwise reusing a key for another course could incorrectly create a second operation.

With PostgreSQL’s default Read Committed isolation, a competing unique-key insert can wait for the first transaction. A subsequent statement can then read its committed result. Implement the conflict lookup as a separate statement. [PostgreSQL concurrency behavior](https://www.postgresql.org/docs/18/transaction-iso.html), [INSERT and conflict handling](https://www.postgresql.org/docs/18/sql-insert.html).

This also handles a lost HTTP response: retrying after commit retrieves the original results, including the original `issued` outcomes.

For recoverable learner-specific failures, use a savepoint around that learner’s certificate and audit writes, then record `failed`. A connection failure or failed overall commit must fail the operation; the UI must not report uncommitted successes.

**Revocation needs a smaller transaction for A7.**

Perform a tenant-scoped conditional update:

```sql
UPDATE certificates
SET status = 'REVOKED'
WHERE tenant_id = $1
  AND id = $2
  AND status = 'ACTIVE'
RETURNING id;
```

Insert the revocation audit only if this updates a row, within the same transaction. If it updates nothing, perform a tenant-scoped lookup to distinguish an already-revoked certificate from a missing one. This endpoint does not need an idempotency-key table.

**List and export should share one filtering and ordering implementation for A5–A6.**

Store `issued_at` as `timestamptz`. Derive the tenant-local calendar date using:

```sql
(issued_at AT TIME ZONE tenant_timezone)::date
```

Use that expression for date sorting and CSV dates; use the tenant-local timestamp for display. PostgreSQL supports named-timezone conversion through `AT TIME ZONE`. [Date/time documentation](https://www.postgresql.org/docs/18/functions-datetime.html).

Every sort must end with a unique tie-breaker:

```sql
ORDER BY local_issue_date DESC, certificate_id ASC
```

That makes equal-date rows repeatable across exports of unchanged data. [PostgreSQL ordering rules](https://www.postgresql.org/docs/18/queries-order.html).

For export, execute one ordered query and write rows incrementally through Go’s `csv.Writer`. Keep multiple database connections available so the export does not monopolize list access. The current 30-second HTTP/proxy timeouts also need adjustment to accommodate the 60-second export requirement. Validate actual performance with the 100,000-row fixture.

**The handler would perform these steps:**

1. Obtain the admin’s tenant and timezone from the existing middleware.
2. Parse and validate the query parameters.
3. Build the shared tenant/search filter and allowlisted sort expression.
4. Query the matching count and requested page.
5. Return certificate data with pagination metadata.

Tenant identity comes exclusively from the resolved admin. Supplying something like `?tenant_id=east` cannot change the scope.

For the example request, the page query would look like:

```sql
SELECT
    c.id,
    c.serial_number,
    l.name AS learner_name,
    co.title AS course_title,
    c.issued_at,
    c.issued_at AT TIME ZONE $3 AS issued_local,
    (c.issued_at AT TIME ZONE $3)::date AS issue_date,
    c.status
FROM certificates c
JOIN learners l
    ON l.tenant_id = c.tenant_id
   AND l.id = c.learner_id
JOIN courses co
    ON co.tenant_id = c.tenant_id
   AND co.id = c.course_id
WHERE c.tenant_id = $1
  AND (
      l.name ILIKE $2 ESCAPE '\'
      OR c.serial_number ILIKE $2 ESCAPE '\'
  )
ORDER BY issue_date DESC, c.id ASC
LIMIT $4 OFFSET $5;
```

The bound values would be:

```text
$1 = "east"                ← resolved admin's tenant
$2 = "%Alex%"              ← escaped literal substring search
$3 = "Australia/Sydney"    ← resolved tenant's timezone
$4 = 25
$5 = (page - 1) × page_size
```

When search is empty, omit the search condition. Escape `%`, `_`, and `\` in user input before adding the surrounding `%`, so those characters are searched literally.

**Sorting needs two specific safeguards.**

First, SQL column names cannot be supplied as ordinary value parameters. Map the accepted API values to fixed SQL expressions:

```go
var sortColumns = map[string]string{
    "learner_name":  "l.name",
    "serial_number": "c.serial_number",
    "issue_date":    "(c.issued_at AT TIME ZONE $3)::date",
}
```

Second, always append `c.id ASC` as a unique tie-breaker. Without a unique ordering, pagination can return unpredictable subsets when sort values are equal. [PostgreSQL pagination guidance](https://www.postgresql.org/docs/18/queries-limit.html)
